## 1. Наскрізні архітектурні принципи

Перш ніж до модулів — три правила, яких дотримується весь дизайн нижче, бо вони прямо випливають зі специфікації:

1. **Шаблон + винятки, а не «плоский» список подій.** Розклад — це не таблиця «на кожен день свій запис». Це `ScheduleTemplate` — тижневий шаблон (§5.1 специфікації), що розгортається на діапазон дат, — плюс шар `DayOverride` (правки, заміни — §5.3, §5.4). `expand()` — детерміноване обчислення, не окрема стадія запису в БД «наперед». Це найважливіше архітектурне рішення проєкту — воно визначає модель даних, і воно детально розписане в розділі 3.
2. **Не будувати те, чого немає в MVP, але не перекривати шлях до другої й третьої черги.** Специфікація прямо каже: «дні народження — джерело даних з'явиться у другій черзі», «нагадування — проєктується так, щоб інші способи сповіщення можна було під'єднати пізніше», «події… програма з самого початку будується так, щоб їх можна було завантажувати автоматично». Це не привід будувати плагінну систему сповіщень заздалегідь (overengineering) — досить, щоб доменні межі (Event, Reminder, Student) не перекручувались, коли ці частини з'являться. Конкретні точки розширення — в розділі 7.
3. **Single-tenant зараз, multi-tenant-ready структурно.** У БД одразу є `user_id` на профільних таблицях і auth через better-auth (яка з коробки підтримує кілька користувачів), але жодної UI- чи бізнес-логіки для «кількох вчителів в одній школі», спільного доступу чи ролей не будується. Це «дешева» готовність — але дешева лише за умови дисципліни запитів із §8.4, інакше `user_id` перетворюється на декоративну колонку.

Не роблю окремого backend-сервісу, черги повідомлень, мікрофронтендів чи GraphQL-шару — для одного користувача й передбачуваного навантаження це чистий overengineering, а Next.js-моноліт із Server Actions якраз і є «чистим і добре спроєктованим» рішенням для такого масштабу.

## 2. Шари застосунку

Next.js fullstack без окремого DTO-шару (як і зафіксовано в tech-stack.md), але з чіткими внутрішніми межами — інакше «типи БД прямо в компонентах» швидко перетворюється на кашу:

```
app/                      # Next.js App Router: сторінки, layout, route handlers
  (app)/                  # оболонка застосунку: темна панель навігації + світле поле
    (calendar)/...        # календар — рік/місяць/тиждень/день
    (schedule)/...        # налаштування року, дзвінки, тижневі шаблони
    (events)/...          # завдання/події (форми створення й редагування)
  (auth)/...              # поза оболонкою: на вході навігації ще немає
  print/...               # друковані вигляди (@media print), без навігації
  api/...                 # Route Handlers лише там, де потрібен non-Server-Action доступ
                          # (майбутні webhook/import-ендпоінти)

lib/
  auth/
    session.ts            # requireUser() — межа авторизації, див. §8.3
  db/
    schema/               # Drizzle-схеми, по одному файлу на агрегат
    queries/              # readonly-вибірки; кожна приймає userId першим аргументом
  domain/
    schedule/
      types.ts            # ResolvedLesson / ResolvedDay — публічний тип домену (§5)
      expand.ts           # чиста функція: шаблон + правила → уроки на діапазон дат
      parity.ts           # обчислення чисельник/знаменник на дату
      calendarRules.ts    # неробочі періоди, дні тижня без уроків, межі семестрів
      boundaries.ts       # резолв символічних меж («до найближчих канікул») у дату
      copyOnWrite.ts      # план правки версії шаблону: обрізка + нова версія (§3.2)
      dates.ts            # календарна арифметика над IsoDate — внутрішня (§8.5)
    events/
      recurrence.ts       # повторювані інформаційні події → конкретні дати
  actions/                # Server Actions — тонкий шар:
                          # requireUser → Zod-валідація → domain/db → revalidate
  validation/             # Zod-схеми, спільні для форм і Server Actions
  time/
    today.ts              # єдине джерело «сьогодні» у зоні Europe/Kyiv (§8.5)

components/               # React, у т.ч. shadcn/ui-обгортки
```

`(app)` — обгортка, а не ще один розділ: вона тримає `layout.tsx` з навігацією, і саме тому `(auth)` та `print` лежать **поруч** із нею, а не всередині. Вимога §7 «друк без панелі навігації» стає властивістю структури, а не домовленістю, яку кожен новий layout мусить пам'ятати. Групи маршрутів не видно в URL, тому на адреси це не впливає.

**Чому саме так.** `lib/domain` — це серце системи: `expand()` (найскладніша й найважливіша логіка в продукті) винесене з Server Actions і з React у чисті, тестовані функції без залежності від БД чи Next.js. Це не «шар заради шару» — специфікація описує неочевидні правила (§4 чергування `NUMERATOR`/`DENOMINATOR` з кількома `ParityAnchor` за рік, §5.1 розгортання з урахуванням `NonTeachingPeriod` і вихідних днів тижня), які потребують модульних тестів окремо від UI. Тому Vitest — частина стеку, а не побажання: `expand()` і `parity()` покриваються тестами з першого дня. Усе інше (CRUD форм, читання списків) іде прямим шляхом Server Action → Drizzle без зайвої абстракції.

## 3. Модель розкладу — ключове рішення

### 3.1 Чому «шаблон + розгортання», а не таблиця уроків на кожен день

Специфікація явно описує механіку, що суперечить наївній моделі «один рядок БД = один урок у конкретний день»:

- Зміна шаблону посеред року **не чіпає минуле** (§5.2) — отже, минуле й майбутнє за одним шаблоном не можуть бути тим самим рядком, який просто «читається на будь-яку дату».
- Скидання чисельника/знаменника **не пов'язане** зі зміною шаблону (§4) — це незалежний параметр обчислення.
- Точкові правки (§5.3) і заміни (§5.4) стосуються **лише одного дня** й не повинні змінювати шаблон.

Якби зберігати кожен урок кожного дня окремим рядком одразу при «застосуванні шаблону», редагування шаблону заднім числом означало б масове перезаписування вже згенерованих рядків — і легко втратити точкові правки, зроблені поверх них. Тому дані розкладу — це три шари, кожен свого призначення:

| Шар | Що зберігає | Коли міняється |
|---|---|---|
| **ScheduleTemplate** (версія шаблону) | Період дії `[validFrom, validTo)` для одного `view` (`OWN`/`CLASS`) + набір `TemplateSlot`: `weekday` × `lessonNumber` × `parity` | Коли вчитель змінює тижневий шаблон (§5.1, §5.2) — завжди створенням нової версії, див. §3.2 |
| **ParityAnchor** (точка відліку парності) | `date` + `parity` (`NUMERATOR` \| `DENOMINATOR`), що діє з цієї дати | Задається один раз на початку року; додається при скиданні після канікул (§4) |
| **DayOverride** (точкове відхилення) | `date` + `lessonNumber` → `EDIT`, `SUBSTITUTION` або `CLEARED` | Точкові правки й заміни (§5.3, §5.4) |

**Розгортання — це читання, не запис.** Календар на будь-який діапазон дат обчислюється функцією `expand()` (`lib/domain/schedule/expand.ts`) під час запиту:

```
для кожного дня в діапазоні:
  визначити parity за найближчим ParityAnchor з date ≤ ця дата
    (парність рахується для кожної дати, і для неробочої теж — це властивість дати)
  якщо день потрапляє в NonTeachingPeriod або в чинне NonTeachingWeekdayRule:
    isNonTeaching = true; шаблон не розгортається — слотів немає
  інакше:
    взяти TemplateSlot тієї версії ScheduleTemplate,
      чий [validFrom, validTo) покриває цю дату, для (weekday, parity)
      (версії може не бути — дірка між версіями дозволена, §3.2 — тоді слотів немає)
  накласти DayOverride для цієї дати — завжди, і в неробочий день теж (§3.4):
    EDIT         → перекриває payload слота; якщо слота немає — додає урок
    CLEARED      → слот стає порожнім; якщо слота немає — no-op
    SUBSTITUTION → показуються обидва: новий payload і replacedOriginal із шаблону;
                   якщо слота немає — replacedOriginal відсутній
```

Це узгоджується напряму зі специфікацією: «зміна шаблону впливає лише на майбутнє» — але **лише за умови інваріантів із §3.2**. Без них твердження хибне.

### 3.2 Версії шаблону: copy-on-write, обрізка, неперетинність

Це найтонше місце всієї моделі, і воно потребує трьох явних інваріантів. Без них природний UI («відкрив тижневий шаблон, змінив клітинку, зберіг») мовчки перепише минуле, бо змінить чинну версію, чий `validFrom` — два місяці тому.

**I1. Версії шаблону immutable щодо минулого — редагування це copy-on-write.**
Редагування чинної версії шаблону ніколи не оновлює її рядки. Замість цього:

```
поточна версія V   [validFrom = 01.09, validTo = 31.12)
вчитель редагує 20.10
  →  V     стає [01.09, 20.10)   ← заморожене минуле, лишається назавжди
  →  V'    стає [20.10, 31.12)   ← нова версія зі змінами
```

Редагування «заднім числом» неможливе за дизайном: точка розрізу — завжди `today()`. Якщо вчителю треба виправити те, що вже минуло, — це `DayOverride` на конкретний день (§5.3 специфікації), а не редагування шаблону.

**I2. Створення нової версії обрізає попередню.**
Сценарій зі специфікації §5.2: у вересні задано шаблон «до кінця семестру», у жовтні — новий «з 20.10». Попередня версія автоматично отримує `validTo = 20.10`. Це не помилка й не потребує підтвердження на рівні моделі — але UI показує попередження «попередній розклад діятиме до 20.10 замість 31.12».

**I3. Інтервали одного виду не перетинаються.**
Це не код, а обмеження БД: з розширенням `btree_gist` —

```sql
EXCLUDE USING gist (
  user_id WITH =, view WITH =,
  daterange(valid_from, valid_to) WITH &&
)
```

Ціна — один рядок міграції. Захищає від найгіршого класу багів у цій моделі: дві версії шаблону покривають одну дату → календар недетермінований залежно від порядку рядків.

**Дірки між версіями дозволені** (період, на який розклад не заданий) — це порожній календар, а не помилка.

**Компроміс, який я свідомо приймаю.** Обчислення «наживо» при кожному відкритті календаря дешевше для одного користувача, ніж матеріалізація (заздалегідь згенеровані рядки на рік наперед), і повністю уникає проблеми «перегенерувати все при редагуванні шаблону». Ціна — обчислення на сервері при рендері місяця/року: річний вид це ~200 навчальних днів × до 10 уроків × 2 види ≈ кілька тисяч обчислених слотів на запит. Для одного вчителя нечутливо. Тригер перегляду — в §9.

### 3.3 Одна таблиця версій, слоти окремо

Види «мої уроки» (OWN) і «уроки класу» (CLASS) мають різні набори полів у клітинці (§5.1: 3 поля проти 5) і незалежні дії «скопіювати з чисельника». Але **версіонування, парність, обрізка інтервалів і copy-on-write у них однакові** — і це найскладніша частина логіки.

Тому: **одна** таблиця версій `ScheduleTemplate(view, validFrom, validTo)` — вся машинерія §3.2 написана й протестована один раз — і **окрема** таблиця слотів, де набір полів залежить від виду. Поля розділені (без nullable-каші «яке поле обов'язкове для якого view»), логіка не дубльована. Валідація payload під конкретний `view` — Zod на межі Server Action, там, де вона й так є.

### 3.4 Заміна, правка і скасування — один рядок `DayOverride`

І «правка» (просто інший урок цього дня), і «заміна» (той самий слот, але з видимим «що було замінено»), і «прибрати урок» (§5.3 прямо цього вимагає) — це один тип рядка `DayOverride` з полем `kind: EDIT | SUBSTITUTION | CLEARED`, а не три таблиці. Різниця між EDIT і SUBSTITUTION — суто в тому, чи UI показує «оригінал» поруч (він і так обчислюється — це те, що дав би шаблон без override). CLEARED — це tombstone: рядок є, вміст порожній, і саме він відрізняє «урок скасовано» від «override відсутній, діє шаблон».

Розділяти в окремі таблиці означало б дублювати логіку «знайти, що діяло б у цей слот за шаблоном» тричі.

**Правило життєвого циклу.** `DayOverride` прив'язаний до дати, а не до версії шаблону, і **переживає зміну шаблону**: специфікація каже «заміна стосується лише конкретної дати й не змінює ні шаблон, ні інші дні» (§5.4). Наслідок, який треба знати: якщо поверх дати з заміною ляже новий шаблон, `replacedOriginal` під `SUBSTITUTION` зміниться — бо він завжди обчислюється з чинної на цю дату версії. Це прийнята поведінка, не баг.

**Неробочий день не скасовує `DayOverride`.** Дві вимоги спеки виглядають суперечливо: §3.1 каже «у дні канікул уроків немає, розклад на ці дні не створюється», а §5.3 — «будь-який окремий день можна відредагувати вручну». Суперечності немає, якщо розділити джерела: `isNonTeaching` глушить **тільки** уроки з `origin = TEMPLATE`, бо саме «розклад на ці дні не створюється»; рядки `DayOverride` вписані на дату руками й рендеряться поверх нього. Тому `ResolvedDay` цілком законно має `isNonTeaching: true` **і** непорожній `lessons`: позначка «канікули/свято» лишається на даті, а вчитель бачить те, що вписав сам — відпрацювання в суботу, захід у святковий день. Це той самий принцип, що й з дірками між версіями: override живе від дати, а не від того, що під ним. Приклад — `docs/architecture/design/expand-fixtures.md` §8.7.

**`replacedOriginal` може бути відсутнім.** Він обчислюється з чинної на дату версії, тож коли під `SUBSTITUTION` немає `TemplateSlot` — інша парність, дірка між версіями, неробочий день — поля просто немає (не `null`, не порожній рядок). Заміна без оригіналу рендериться як звичайний доданий урок. Симетрично `CLEARED` без слота під ним — no-op, а не помилка: tombstone нічого не гасить. Приклад — `expand-fixtures.md` §8.8.

### 3.5 Парність: `NUMERATOR` / `DENOMINATOR`

`ParityAnchor` — це просто список точок «з цієї `date` діє ось такий `parity`». За замовчуванням у ньому **один запис**: дата початку `AcademicYear` + значення, яке вчитель обрав у налаштуваннях («рік починається з чисельника», §4). Кожне скидання після канікул — ще один запис у той самий список. Окремої сутності «скидання» немає: початкове значення і скидання — одне й те саме.

**Формула:**

```
parity(d) = anchor.parity XOR ( weeksBetween( startOfISOWeek(anchor.date),
                                              startOfISOWeek(d) ) % 2 )
де anchor = останній ParityAnchor з date ≤ d
```

**Тиждень починається з понеділка** (ISO). Це стосується і обчислення парності, і відображення тижня в календарі.

**Тиждень канікул «з'їдає» парність** — лічильник рахує календарні тижні й не пропускає тижні без уроків. Це прийнятий дефолт, а не істина: специфікація свідомо не фіксує цю поведінку, бо для неї є ручний механізм скидання (§4). Дефолт живе **всередині `parity.ts` і більше ніде** — змінити його означає змінити одну функцію та її тести, без міграцій і без змін у моделі даних. Питання відкрите — див. §10.1.

## 4. Модель даних (огляд, не повна DDL)

```
User                    — вчитель (auth)

AcademicYear            — dateFrom, dateTo
                          (початкова парність зберігається не тут, а першим
                           ParityAnchor на dateFrom — див. §3.5)
Semester                — yearId, порядковий номер (1|2), dateFrom, dateTo
NonTeachingPeriod       — yearId, kind: BREAK | PUBLIC_HOLIDAY | OTHER,
                          name, dateFrom, dateTo
                          (свято — це період довжиною в один день)
NonTeachingWeekdayRule  — день тижня, виключений з розкладу,
                          + validFrom і резолвлена межа дії (див. §8.1)
BellSchedule            — час початку/кінця для номерів уроків 0–9

ParityAnchor            — date → NUMERATOR | DENOMINATOR
ScheduleTemplate        — view: OWN | CLASS; [validFrom, validTo)
TemplateSlot            — templateId, weekday, lessonNumber, parity
                          + payload за видом:
                            OWN   : subject, className
                            CLASS : subject, teacherName, zoomLink, note
DayOverride             — date, lessonNumber, view,
                          kind: EDIT | SUBSTITUTION | CLEARED,
                          payload (порожній для CLEARED)

Event                   — kind: DEADLINE | INFO; title, note; дата/діапазон;
                          INFO: recurrenceKind з резолвленою межею дії
                          DEADLINE: одноразовий, поле done
```

Повна DDL — `docs/architecture/design/schema.md` (T-003): типи колонок,
обмеження, індекси, порядок міграцій і seed. Тут — лише склад моделі й причини.

**Чому всі неробочі періоди — одна таблиця.** Канікули (осінні/зимові/весняні), державні свята та позапланові дні (карантин, актований мороз) відрізняються лише назвою й довжиною. `expand()` робить **одну** перевірку «чи дата в неробочому періоді» замість трьох, а додати новий вид вихідних = вставити рядок, не міняти код. Жорстко зашиті «три канікули» дали б ту саму функціональність меншою ціною лише на перший погляд — реальні школи додають перерви поза планом.

Окремо лишається `NonTeachingWeekdayRule` (§3.4 специфікації, «методичний день») — це не датовий інтервал, а правило по дню тижня; інша природа, інша перевірка.

**Чому семестри — рядки, а не колонки в `AcademicYear`.** Два рядки замість чотирьох колонок; і це автоматично знімає питання «семестр суцільний чи розірваний канікулами»: семестр — суцільний діапазон, канікули всередині нього фільтруються окремим правилом (`NonTeachingPeriod`), бо `expand()` однаково перевіряє обидва. Різниці в результаті немає, модель простіша.

**Чому DEADLINE не повторюється.** Свідоме рішення: `done` — одне поле на подію, тому повторюваний дедлайн означав би «виконав один раз — закрилася вся серія». Замість стану на кожне входження (зайва таблиця під функціонал, якого ніхто не просив) — дедлайни в MVP одноразові. Повторення лишається тільки в INFO-подій, де стану виконання немає взагалі. Якщо повторювані дедлайни колись знадобляться — див. §9, тригер зафіксовано.

**Чому уроки, які вчитель веде у своєму класі, не потребують дедуплікації (§6.2 — «прибирати дублювання не потрібно»).** Це архітектурний подарунок від специфікації: два незалежні набори слотів (OWN і CLASS) просто обидва можуть містити запис на той самий слот — рендер календаря лише додає позначку «це веду я» на CLASS-стороні, звіряючи урок класу з **розгорнутим OWN-днем тієї самої дати**: збігаються `lessonNumber` і `subject`. Ніякого зв'язку в БД між цими двома рядками не потрібно.

Порівнювати треба саме `subject`, а не лише `lessonNumber`: у той самий слот вчитель може вести власний урок в іншому класі, і тоді збіг за номером позначив би чужий урок як «мій» (приклад — `docs/architecture/design/expand-fixtures.md` §8.6). І порівнювати треба з результатом `expand()`, а не з `TemplateSlot`: `DayOverride` на цю дату міняє відповідь. Залишок питання — предмети зберігаються вільним текстом — див. §10.6.

**Довідники — вільний текст.** Предмет, клас, ПІБ учителя зберігаються рядками, без окремих таблиць-довідників. Для одного вчителя нормалізація не окупається. Ціна відома й прийнята: можливі «Математика» / «математика». Пом'якшення — автопідстановка з `DISTINCT` уже введених значень у формі. Тригер перегляду — в §9.

## 5. Календар як похідна, а не сутність

Календар (§6) не має власної таблиці «календарних днів». Кожен вид (рік/місяць/тиждень/день) — це просто інший діапазон, переданий у ту саму функцію `expand()` плюс вибірка `Event` за той самий діапазон. День народження (друга черга) додасться як ще одне джерело міток на дату — без зміни моделі уроків.

**Одне уточнення до «немає DTO-шару».** Для CRUD-форм типи Drizzle справді течуть прямо в компоненти. Але **календар споживає не рядок таблиці**, а результат злиття трьох джерел (слот шаблону + парність + override). Цей тип існує явно і є публічним типом домену:

```
ResolvedLesson  — lessonNumber, timeFrom, timeTo, payload,
                  origin: TEMPLATE | EDIT | SUBSTITUTION,
                  replacedOriginal?: payload   ← лише для SUBSTITUTION
                  isTaughtByMe?: boolean       ← лише для CLASS-виду
ResolvedDay     — date, parity, isNonTeaching, lessons: ResolvedLesson[]
```

Це не відступ від принципу «без DTO», а його межа: зшивання трьох джерел робиться **один раз у домені**, а не по-своєму в кожному компоненті календаря, друку й майбутнього експорту.

**Межа рендеру: `CalendarDay` (T-007).** Екранам календаря потрібні ще дві речі, яких у `ResolvedDay` свідомо немає: назва `NonTeachingPeriod`, що затінює день, і уроки, зняті `DayOverride.kind = CLEARED`. Друге — не недогляд `expand()`, а його правило: tombstone не має повертатися уроком (`design/expand-fixtures.md` §8.8), тоді як специфікація §5.3 вимагає, щоб учитель **бачив** скасований урок закресленим, а не коротший день. Тому `CalendarDay = ResolvedDay + cancelled + nonTeachingName` збирається один раз, тим самим доводом, що й `ResolvedLesson`: інакше день, тиждень, місяць, рік і друк рахували б це кожен по-своєму. Скасовані уроки обчислюються як різниця двох розгортань того самого діапазону — звичайного і без `overrides`, — тож правило «який слот діяв на цю дату» лишається тільки в `expand()`. Механіка — `design/T-007-calendar-views.md`.

## 6. Друк (§7)

Окремий route `/print/...`, що рендерить ту саму похідну модель (`ResolvedDay[]` + `Event[]`) у верстку «для друку»: без навігації, чорно-біла, з розбиттям на аркуші через `@media print` і CSS-правила розривів сторінок. PDF отримується вбудованим «Зберегти як PDF» браузера.

**Чому так, а не серверний рендер.** Специфікація §7 вимагає *сторінки з окремим оформленням для друку* — і саме це `@media print` дає без жодної інфраструктури. Puppeteer/headless Chromium — це +300–400 МБ образу й піки пам'яті на VPS; він потрібен лише тоді, коли **сама програма** має породжувати файл (надіслати поштою, зберегти в архів), чого в MVP немає (§11: сповіщень немає). Заміна пізніше дешева саме тому, що друк споживає ті самі доменні функції, що й UI-календар, а не окрему копію логіки: міняється рендерер, не модель. Тригер — у §9.

## 7. Точки розширення під другу й третю чергу

Специфікація прямо вимагає не переробляти ядро, коли з'являться:

- **Список класу / дні народження (§9).** `Student` — нова таблиця, не пов'язана з розкладом. День народження — просто ще один producer міток для календаря (той самий контракт, що й `Event`: дата → мітка). Жодних змін у `ScheduleTemplate`/`DayOverride`.
- **Сповіщення (§6.3).** `Event` типу DEADLINE вже спроєктований як окрема сутність зі своїм станом (`done`); коли з'явиться пошта/месенджер — це новий обробник, що читає ті самі дедлайни. Тоді ж (і не раніше) з'являється таблиця черги й **окремий `worker`-сервіс** у Compose — не таймер усередині веб-процесу, див. tech-stack.md. Модель `Event` при цьому не змінюється.
- **Імпорт (§10).** Двокроковий процес («прочитати файл → розкласти по календарю») природно лягає на вже наявні точки входу: розпізнаний рядок Excel просто стає `Student` або `Event` через ту саму валідацію (Zod), що й ручне введення з форми. Окремого імпорт-шару зараз не будую — знадобиться лише парсер файлу, решта конвеєра вже є.

Я свідомо **не** створюю зараз абстрактний `NotificationChannel` інтерфейс чи `ImportSource` плагінну систему — жодного коду під них ще немає, а передчасна абстракція без другого реального випадку використання це здогадки, а не дизайн.

## 8. Технічні наскрізні рішення

### 8.1 Символічні межі дії резолвляться при записі

Специфікація робить це наскрізним правилом (§3.4, врізка): будь-який повтор задається «до дати Х» / «до найближчих канікул» / «до кінця семестру». Це стосується `NonTeachingWeekdayRule`, `ScheduleTemplate.validTo` і повторюваних INFO-подій.

**Рішення: символ резолвиться в конкретну дату в момент запису.** Зберігається пара: `boundaryDate` (обчислена дата, з якою працює вся логіка) + `boundaryKind` (`DATE | NEXT_BREAK | END_OF_SEMESTER` — лише для відображення в UI: «до зимових канікул»).

**`boundaryDate` — виключна межа.** Правило діє на дату `d`, поки `d < boundaryDate` — так само, як `validTo` у `ScheduleTemplate`. Тому `NEXT_BREAK` резолвиться в **перший день** найближчих канікул, а `END_OF_SEMESTER` — у перший день після семестру. Одне правило на всі межі дії. Це не стосується діапазонів самих сутностей — `AcademicYear`, `Semester`, `NonTeachingPeriod` та `Event` мають перший і **останній** день, тобто їхній `dateTo` інклюзивний. Саме тому `END_OF_SEMESTER` — це `Semester.dateTo` плюс один день.

**Чому не зберігати символ і резолвити при читанні.** Тоді `expand()` мусив би резолвити межі проти `AcademicYear`, який вчитель може відредагувати будь-коли (§3 спеки: «усі ці параметри можна змінити будь-коли»). Зсув дат зимових канікул у січні мовчки переписав би те, що вже минуло, — прямо ламаючи §5.2 «історія не переписується». Ціна прийнятого рішення: зміна дат канікул **не** зсуває вже задані межі автоматично; UI має підказати «перевірте правила, що закінчувались на цих канікулах».

**Звідки береться початок дії.** Межа резолвиться проти дати, з якої правило починає діяти, а не проти «сьогодні» взагалі: екран налаштувань року пише `validFrom` як **пізнішу з двох дат** — перший день `AcademicYear` і сьогодні (`ruleValidFrom()` у `lib/domain/schedule/boundaries.ts`, `decisions/ADR-004-year-setup-valid-from.md`). Правка правила зберігає наявний `validFrom`, тож змінюється те, де правило закінчується, а не тижні, які воно вже охопило.

Підказку «перевірте правила, що закінчувались на цих канікулах» дає форма редагування неробочого періоду (T-009).

### 8.2 Валідація

Одна Zod-схема на форму — межа довіри в Server Action і водночас те, з чого форма бере свої поля; окремого рівня DTO немає, як і зафіксовано в tech-stack.md.

Форми надсилаються через `<form action={…}>` і `useActionState`, **без react-hook-form**: схема парситься тільки в Server Action, а на клієнті з неї береться карта імен полів (`*_FIELD`, оголошена `as const satisfies Record<keyof Input, string>`) — тож перейменований ключ ламає типізацію форми. Наслідок, заради якого це й зроблено: форми працюють із вимкненим JavaScript. Чому саме так і чого коштувала б альтернатива — `decisions/ADR-005-forms-use-action-state.md`.

### 8.3 Авторизація — у `lib/db/queries`, не в middleware

Перевірка сесії живе в `lib/auth/session.ts::requireUser()`, яка викликається **на вході кожної Server Action і кожної query**. Middleware лишається — але виключно як редірект неавторизованого на сторінку входу, тобто як UX, а не як межа безпеки.

Причина: middleware в Next.js не є надійною межею для прямих викликів Server Actions і Route Handlers (це відомий клас помилок, підсвічений зокрема CVE-2025-29927). Складнішого RBAC не потрібно, поки не з'явиться multi-tenant — але сама перевірка має бути там, де дані, а не перед маршрутизатором.

### 8.4 Дисципліна `user_id`

«Multi-tenant-ready через колонку» реальний лише тоді, коли жоден запит не може її забути. Правило, що діє з першого комміту:

- усі функції в `lib/db/queries` приймають `userId` **першим аргументом**;
- кожна мутація отримує `userId` з `requireUser()` **до будь-якої іншої роботи** і фільтрує ним **кожен** statement — `where(eq(table.userId, userId))` у власному запиті, або `ON DELETE CASCADE` від рядка, який вже так відфільтрований. Першим аргументом його не передають: Server Action має сигнатуру, яку задає `useActionState` (`ADR-005`), тому місця для нього там просто немає — і саме тому дисципліна тут інша за формою, але та сама по суті;
- `userId` береться виключно з `requireUser()`, ніколи з параметрів запиту чи форми;
- усі профільні таблиці мають `user_id NOT NULL` і індекс, що починається з нього.

Без цього перехід на кількох користувачів означатиме ручну ревізію кожного запиту — тобто «дешева готовність» виявиться найдорожчою частиною міграції.

### 8.5 Дати й час

- Час дзвінків — тип `time` (§3.3 спеки), прив'язки до дати немає.
- Дати уроків і подій — тип `date`, без часової зони: школа в одному часовому поясі.
- **Жодних `new Date()` у доменному коді.** «Сьогодні» береться тільки з `lib/time/today.ts`, який обчислює дату у зоні `Europe/Kyiv`. Контейнер працює в UTC, і о 01:00 за Києвом наївний `new Date()` дає вчорашню дату — це ламає точку розрізу copy-on-write (§3.2) і підсвічування «сьогодні» в календарі.
- Тиждень починається з понеділка скрізь: парність, тижневий вид, тижневий шаблон.

## 9. Зафіксовані компроміси та тригери перегляду

Кожен рядок — свідомо прийнята ціна. Тригер — умова, за якої рішення переглядається; поки тригер не настав, обговорювати нічого.

| Рішення | Що виграємо | Ціна | Тригер перегляду |
|---|---|---|---|
| **`expand()` при читанні**, а не матеріалізація рядків (§3.1) | Немає масового перезапису при зміні шаблону; правки не губляться; історія природно незмінна | Обчислення на кожен рендер: ~кілька тисяч слотів на річний вид | Час рендеру річного виду > ~300 мс, або перехід на багатьох користувачів. **Реакція: кеш результату `expand()` на рівні Server Action / `unstable_cache`, а не зміна моделі** |
| **Друк через `@media print`**, серверний PDF відкладено (§6) | Нуль інфраструктури, малий образ, працює одразу | Немає програмної генерації файлу; точність розбиття на аркуші обмежена можливостями браузера | Програмі треба **самій** породити файл (надіслати, зберегти в архів) або замовник вимагає посторінкової верстки, недосяжної в CSS. Реакція: додати рендерер, модель не чіпати |
| **Одна таблиця версій шаблону + слоти за видом** (§3.3) | Версіонування, обрізка й copy-on-write написані один раз | Payload слота типізується за `view` у Zod, а не в БД | Набори полів OWN/CLASS розійдуться настільки, що з'явиться третій вид або складні зв'язки в payload |
| **Дедлайни без повторення** (§4) | Немає таблиці стану на входження | Повторюваний дедлайн доводиться заводити кількома записами | Замовник просить повторювані завдання з окремим «виконано» на кожне. Реакція: `EventOccurrence(eventId, date, done)`, `Event` не змінюється |
| **Довідники вільним текстом** (§4) | Немає CRUD-екранів для предметів і класів | Можливі різнописання; групування у звітах ненадійне | Звіти з групуванням за предметом, або друга черга зі списком класу, де клас стає сутністю |
| **Символічні межі резолвляться при записі** (§8.1) | `expand()` детермінований; історію неможливо переписати зміною дат канікул | Зміна дат канікул не зсуває вже задані межі автоматично | Вчитель регулярно скаржиться, що після правки канікул треба переставляти правила вручну. Реакція: разова дія «перерахувати межі», не зміна моделі |
| **Postgres замість SQLite** (tech-stack) | Немає майбутньої міграції БД | +сервіс у Compose, потрібен бекап | Одностороннє рішення, переглядати нічого |
| **Single-tenant, але з `user_id`** (§1, §8.4) | Дешева готовність до кількох користувачів | Дисципліна запитів у кожному файлі | Поява другого реального користувача → ролі, шаринг, ізоляція на рівні запитів уже є |
| **Черга й cron не будуються** (tech-stack) | Немає порожньої інфраструктури | Перша фонова задача потребує окремого сервісу | Перша реальна фонова задача (сповіщення §6.3 або імпорт §10) |
| **Без кешування на старті** | Простіший потік даних, немає інвалідації | Кожен рендер рахує заново | Той самий, що й у першому рядку |

## 10. Невирішені питання

Формат: суть → вартість рішення → наслідки, якщо помилитись.

### 10.1 Парність і тижні канікул

**Суть.** Якщо канікули займають повний тиждень, наступний навчальний тиждень продовжує чергування (тобто тиждень канікул «з'їв» одну позицію) чи повторює парність останнього навчального тижня? Специфікація свідомо не фіксує цього — вона дає ручний механізм скидання (§4), який закриває будь-який випадок. Але поведінка **за замовчуванням**, коли вчитель нічого не скидав, коду все одно потрібна.

**Прийнято зараз:** «з'їдає» — лічильник рахує календарні ISO-тижні поспіль.

**Вартість зміни.** Мінімальна й обмежена: дефолт живе в одній чистій функції `parity.ts` і в її тестах. Немає ні міграцій, ні змін у моделі даних, ні перезапису збережених даних — `ParityAnchor` описує точки, а не результат.

**Наслідки, якщо дефолт неправильний.** Календар після кожних канікул показує зсунуту парність, доки вчитель не поставить скидання вручну. Дані при цьому не псуються — зіпсоване лише відображення, і воно виправляється однією дією в UI. Тому ризик прийнятний, а рішення можна відкласти до першого реального навчального року.

**Що потрібно:** підтвердження від замовника (як реально працює його школа) — бажано до першого релізу, не блокує розробку.

### 10.2 Мобільна версія (специфікація §1)

**Суть.** Специфікація вимагає **повнофункціональної** мобільної версії: усе, що можна зробити на комп'ютері, — з телефона. Найважчі екрани: тижневий шаблон (6 днів × до 10 уроків — таблиця, яка фізично не поміщається в 390 px) і річний вид календаря. Це не питання «Tailwind розтягне» — це окремий патерн взаємодії (наприклад, день-центричний ввід шаблону замість таблиці).

**Вартість.** Найвища серед відкритих питань, і вона **структурна**: рішення визначає, як розбиті компоненти календаря й редактора шаблону. Домену (`expand`, `parity`, модель даних) не стосується зовсім — там вплив нульовий.

**Наслідки, якщо відкласти.** Якщо спроєктувати десктопну таблицю й потім адаптувати — з великою ймовірністю доведеться переписувати редактор шаблону, а не «дописати CSS». Якщо ж домовитись про патерн до початку UI — вартість нульова, бо коду ще немає.

**Рішення (Q-002, ухвалено до старту UI).** День-центричний потік. На вузькому екрані і календар, і редактор шаблону показують **один день** — список уроків цього дня, з переходом між днями; таблиця 6 × 10 з'являється лише з планшетної ширини вгору. Отже, «день» — це спільний компонент, а тижнева таблиця — обгортка над сімома такими днями, а не навпаки: сітка, адаптована під 390 px, означала б переписування редактора, а не додавання CSS.

Наслідок для структури компонентів: `ResolvedDay` — межа, на якій розділені компоненти календаря й редактора шаблону; вид (день/тиждень/місяць/рік) відрізняється лише діапазоном, який передається в `expand()` (§5), а не набором компонентів.

**Статус:** закрито. Домену рішення не торкається зовсім — `expand()`, `parity()` і модель даних від нього не залежать.

### 10.3 Перелік друкованих звітів (специфікація §12.1)

**Суть.** Які саме документи потрібні: розклад на тиждень, на семестр, список класу, щось іще.

**Вартість.** Низька й ізольована: кожен звіт — окрема сторінка під `/print/...`, що споживає вже наявні `ResolvedDay[]` / `Event[]`. Додати звіт = додати сторінку.

**Наслідки, якщо не знати зараз.** Практично жодних для архітектури. Єдиний ризик — якщо якийсь звіт потребує даних, яких у моделі немає взагалі (наприклад, підсумкові години за предметом за семестр — це агрегація, яку теж дає `expand()`, але про неї треба знати). Уточнити варто до реалізації §7, не раніше.

### 10.4 Технологія серверного рендеру PDF

**Суть.** Puppeteer vs `@react-pdf/renderer` — якщо серверний рендер узагалі знадобиться.

**Вартість.** Нульова зараз: рішення відкладене разом із самою функцією (§6, тригер у §9).

**Наслідки.** Немає — друк споживає ті самі доменні функції, тож заміна рендерера не торкається моделі.

### 10.5 Структура контактів учня (специфікація §12.2)

**Суть.** Один основний контакт чи кілька (мама/тато/бабуся) із зазначенням ролі.

**Вартість.** Питання другої черги; на MVP не впливає. Специфікація вже попереджає, що знадобиться кілька, тож `Student` від початку проєктується так, щоб контакти можна було винести в окрему таблицю.

**Наслідки, якщо вгадати неправильно.** Одна міграція «одне поле → окрема таблиця» на порожній або майже порожній таблиці учнів. Дешево, тому рішення справедливо відкладене.

### 10.6 Ознака «цей урок веду я» при однакових предметах (§4)

`isTaughtByMe` звіряє `lessonNumber` і `subject` з розгорнутим OWN-днем (§4). Лишається випадок, який цим не ловиться: у класі той самий предмет у той самий слот веде інший учитель, а вчитель у цей час веде свій предмет із тією ж назвою в іншому класі — збіг за `subject` дасть хибне «це веду я». Предмети — вільний текст (§4), тож різнописання («Математика» / «математика») дає й зворотну помилку.

**Дефолт до відповіді:** порівняння за `subject`, ризик прийнятий; він проявляється лише в описаній рідкісній конфігурації й лише на позначці рендеру.

**Альтернатива:** явне поле на `TemplateSlot` виду CLASS («цей урок веду я»), яке вчитель ставить руками. Точне, але це колонка — тобто зміна в T-003 і T-004.

Питання — Q-006.

## 11. Наступний крок

Модель вважається готовою до перекладу в Drizzle-схему (`lib/db/schema`). Перед написанням міграцій пропоную одну перевірку на папері: розписати вручну один тиждень, у якому одночасно є **зміна шаблону посеред тижня, скидання парності після канікул і заміна уроку** — і звірити, що `expand()` за правилами §3 дає очікуваний результат. Це найдешевший спосіб зловити помилку в інваріантах §3.2 до того, як з'являться дані.

**Зроблено.** Перевірка виконана й лежить у `docs/architecture/design/expand-fixtures.md` (T-001): п'ять тижнів жовтня–листопада 2026 з очікуваним `ResolvedDay[]` на кожну дату для обох видів. Вона й підсвітила уточнення в §4 (`isTaughtByMe`), §8.1 (виключність `boundaryDate`) і §10.6.

**Зроблено (T-003).** Модель переведена в повну DDL —
`docs/architecture/design/schema.md`. Вона підсвітила чотири речі: початкова
парність прибрана з `AcademicYear` (дублювала `ParityAnchor` — §4 і glossary
виправлені цим же коммітом), `NonTeachingWeekdayRule` отримав `validFrom`
(F-3 фікстур), а `BellSchedule` без прив'язки до року і `DayOverride` без
власного часу зафіксовані як прийняті обмеження — див. §12 того документа.
