# Відомі проблеми harness

**Дата:** 1 жовтня 2026 р.
**Статус:** робочий документ. Тут зібрані слабкі місця harness, які ще не мають тікетів. Пункт, для якого заведено тікет, отримує посилання на `T-NNN`. Вирішений пункт видаляється, а його рішення записується в документ, якому воно належить.

Як harness влаштований — у `docs/architecture/harness.md`. Тут тільки те, що в ньому працює погано або не покрито зовсім.

Мова документа — українська проза з англійськими іменами.

## 1. Незалежне рев'ю після `/teachers-ticket`

### 1.1 Поточний стан

Після того як `/teachers-ticket` завершив роботу:

- PR відкритий, тікет має `status: done`, чекбокси acceptance criteria поставлені;
- `/teachers-fix-loop` вийшов з `converged` або з `cap`;
- кожен раунд self-review пройшов на `--effort medium`, з `--merge=no` і `--no-comment`;
- merge не зроблено: self-review його не робить.

Наступний крок — незалежне рев'ю і merge. Для цього harness має один інструмент: `/teachers-review` у standalone-режимі, в окремій сесії:

```
/teachers-review <pr> --effort high --merge=no
```

Порівняно із self-review він дає:

- **чистий контекст** — сесія не бачить розмови автора, його плану й аргументів;
- **ширше читання** — на `high` фаза 2 читає розділи `architect-overview.md` для зачеплених шарів, `glossary.md` і `docs/tech-stack.md`. На `medium` їх немає, якщо тільки тікет не посилається на них у `refs:` (`harness.md` §7.4);
- **ширший `/code-review`** — `high` замість `medium`;
- **коментарі в PR** — `--comment` за замовчуванням.

Схема в `harness.md` §3.1 закінчується на «`ci.yml` → merge», і крок незалежного рев'ю в ній не описаний.

### 1.2 Слабкі місця

**A. Немає шляху «findings незалежного рев'ю → виправлення».** `/teachers-review` нічого не редагує (`ADR-014`). Інструменти, які редагують, не підходять:

- `/teachers-fix-loop` вимагає `--state` — це `.gate/run.json`. Він git-ignored і існує тільки у worktree автора. Ліміти рахуються з історії: `pushesAfterOpening` — з історії гілки, номер раунду — з `.gate/findings.json`. Якщо self-review цикл уже витратив ліміти, новий цикл одразу поверне `exit: "cap"`.
- `/teachers-ticket --resume` продовжує з фази, записаної в `run.json`. Фаза 7 уже завершена, і повернення до неї не описане.

**B. Тікет уже має `done`.** Якщо незалежне рев'ю знайде невиконаний acceptance criterion, треба зняти чекбокс, повернути `status: in-progress` у тікеті та в `docs/backlog/README.md`. Це робота фази 7 `/teachers-ticket`, а з іншої сесії її ніхто не запускає.

**C. Відхилені findings ніхто не бачить.** Disposition `rejected` разом із цитатою-спростуванням зберігається тільки в `.gate/findings.json` — локальному git-ignored файлі. Фаза 7 переносить у тіло PR лише `deferred` і `## Outside this change`. Наслідки:

- незалежний рецензент може знову підняти finding, який автор уже обґрунтовано відхилив, і не знатиме про відхилення;
- людина, що читає PR перед merge, не бачить, що саме було відхилено і чому.

**D. Незалежність лише часткова.** Та сама модель, той самий скіл, ті самі документи, той самий `teachers-review-contract` (`model: opus`). Чистий контекст прибирає упередженість автора, але не прибирає упередженість методу. Сліпі зони self-review і незалежного рев'ю будуть схожі.

### 1.3 Workaround

Поки змін у harness немає:

1. **Окремий worktree для рецензента**, щоб `gh pr checkout` не перемикав гілку під сесією автора:
   ```sh
   git worktree add ../teachers-review origin/main
   ```
   Нова сесія Claude Code в цьому каталозі. `SessionStart` hook сам робить fetch.
2. **Рев'ю:** `/teachers-review <pr> --effort high --merge=no`. `--effort max` — коли потрібне читання залежного коду і фаза 6.
3. **Нуль findings** → merge вручну після зеленого CI (`gh pr checks <pr>`).
4. **Є findings** → виправлення у worktree автора як direct change на тій самій гілці. Коміт `T-NNN review fixes: <what>`, `npm run gate`, push. Потім знову `/teachers-review` у сесії рецензента.
5. **Постраждав acceptance criterion** → вручну зняти чекбокс і повернути `status: in-progress` у тікеті та в `README.md`, в тому самому коміті.
6. **Щоб рецензент не повторював відхилене (C)** → перед незалежним рев'ю вручну перенести `rejected` з `.gate/findings.json` у тіло PR, разом із цитатами.
7. **Для більшої незалежності (D):**
   - інша модель у сесії рецензента (`/model`);
   - інша лінза: `/security-review` або `/code-review high <pr>` окремо від документів;
   - людина читає PR останньою.

### 1.4 Можливі рішення

| Слабке місце | Рішення | Вартість |
|---|---|---|
| C | Фаза 7 `/teachers-ticket` (і `/teachers-fix-loop` для PR без тікета) переносить кожен `rejected` у тіло PR: finding, цитата-спростування, документ. | мала: одна інструкція у двох скілах; рецензент і людина бачать відхилене |
| A, B | Окремий post-ticket крок — новий скіл (робоча назва `teachers-address-review`) або нова фаза `/teachers-ticket`. Бере коментарі незалежного рев'ю з PR як findings і застосовує ті самі чотири dispositions. Ліміти рахуються окремо від self-review циклу. Має право повернути тікет з `done` у `in-progress`. | середня: новий контракт, нові ліміти в `scripts/gate/caps.ts`, тест у `skills.test.ts`; ймовірно ADR, бо це змінює `ADR-014`/`ADR-017` |

| усі | Додати крок незалежного рев'ю в `harness.md` §3.1, коли буде обране рішення для A/B. | мала |

## 2. `npm run gate` не запускає `npm`-перевірки на Windows

### 2.1 Поточний стан

`scripts/gate/index.ts` запускає перевірки так: `spawnSync(command, args, { encoding, maxBuffer })`, без `shell`. На Windows `npm` — це shim `npm.cmd`, і без `shell` `spawnSync` його не знаходить.

### 2.2 Слабке місце

Кожна перевірка, що починається з `npm` (`lint`, `typecheck`, `test`, `build` і т. д.), повертає `FAIL` за 0.0s без жодного виводу. Gate завжди червоний на Windows, хоча самі перевірки проходять. У ledger це записано як звичайні `failed`, тому `--report` теж відмовляє.

### 2.3 Workaround

Запустити перевірки напряму (`npm run lint`, `npm run typecheck`, `npm test`, `npm run build`) і в тілі PR написати, що gate на цій машині не працює, і чому. Авторитетний вердикт — `ci.yml`.

### 2.4 Можливі рішення

- `shell: process.platform === "win32"` у виклику `spawnSync` — найменша зміна. Аргументи в `checks.ts` статичні, тому ризику з екрануванням немає.
- Або на Windows підставляти `npm.cmd` замість `npm`.
- У будь-якому разі — тест, який фіксує, що `ENOENT` від `spawnSync` стає `failed` з причиною, а не порожнім виводом. Зараз код, що запускає перевірки, `result.error` не читає (читає тільки виклик `gh pr checks`).

## 3. `vam-handoff` без префікса `teachers-`

### 3.1 Поточний стан

`ADR-002` вимагає префікс `teachers-` для кожного скіла й агента в `.claude/`. `.claude/skills/vam-handoff/` був у репозиторії ще до цього ADR (initial commit) і префікса не має.

### 3.2 Слабке місце

Невідповідність ADR. Невеликий ризик колізії з однойменним глобальним скілом користувача — саме від цього захищає `ADR-002`.

### 3.3 Workaround

Не потрібен: скіл працює і не входить у цикл.

### 3.4 Можливі рішення

- Перейменувати на `teachers-handoff`.
- Або видалити з репозиторію, якщо це особистий скіл, який краще тримати в `~/.claude/skills/`.
