## Goal

Translate the T-003 document into `lib/db/schema` (one file per aggregate) and
generate the first migration, with the `ScheduleTemplate` overlap constraint
proven by a test that talks to a real Postgres.

## Acceptance criteria

- [x] `lib/db/schema/*.ts`, one file per aggregate, matching T-003 exactly.
- [x] better-auth's tables generated into `lib/db/schema/auth.ts` and included in
      the same first migration: every profile table has a foreign key to
      `user(id)`, so `user` cannot wait for T-006
      (`docs/architecture/design/schema.md` §5.1). `requireUser()` and the
      sign-in flow stay in T-006.
- [x] First migration generated by `drizzle-kit` and applied to a clean
      database, including the `btree_gist` extension.
- [x] Integration test: a second template edit on the same day updates the
      current version in place instead of cutting it to zero length
      (`docs/architecture/design/schema.md` §4.7).
- [x] `updated_at` is maintained by `.$onUpdate()` on every Drizzle table that
      has the column — the SQL default only covers `INSERT`
      (`docs/architecture/design/schema.md` §1).
- [x] Integration test: inserting two `ScheduleTemplate` rows whose
      `[validFrom, validTo)` overlap for the same `(user_id, view)` is rejected
      by the database; the same rows with `view` differing are accepted.
- [x] Integration test: a gap between two versions is accepted (overview §3.2 —
      holes are legal).
- [x] Seed script runs against a clean database and produces the T-001 fixture
      scenario. The fixture document is the single source for that scenario —
      the seed is derived from it, and the T-005 test expectations are too;
      neither restates it independently.
- [x] `drizzle-kit migrate` documented in `README.md` as an explicit deploy step.

## Notes

Implemented in the `claude/docs-backlog-ticket-scmmu3` branch.

**Layout.** One file per aggregate in `lib/db/schema`, plus two files that are
not aggregates: `enums.ts` (five of the eight enum types are shared by two or
more tables) and `columns.ts` (the `id` / `user_id` / `created_at` / `updated_at`
helpers of `docs/architecture/design/schema.md` §1, as functions rather than a
shared object — a Drizzle column builder is mutated by `.notNull()`, so two
tables sharing one instance would edit each other's definition).
`index.ts` is the barrel `getDb()` registers.

**`account.issuer` is a hand-applied correction to the generated `auth.ts`.**
The published `@better-auth/cli` is 1.4.x; this project depends on `better-auth`
1.7.x, whose `getAuthTables()` declares a required `issuer` field on `account`
that the older generator does not emit — and `signUpEmail` writes it, so the
generated schema would have failed on the first sign-in in T-006. The CLI also
cannot read `lib/auth/auth.ts`, which exports a `getAuth()` factory rather than a
bare `auth`, so the config was handed to it as a temporary file. Both are
recorded in the header of `lib/db/schema/auth.ts`: regenerating means diffing,
not overwriting.

**Migration set** is 0000 (custom, `btree_gist`), 0001 (generated), 0002
(custom, the three `EXCLUDE USING gist` constraints), exactly as §9 orders them.
Verified end to end against a clean database: drop, `db:migrate`, `db:seed`,
`test:integration`.

**Tests.** `*.integration.test.ts` files are excluded from `npm test` and run by
`npm run test:integration` against a migrated database, so a checkout without
Docker still has a green unit suite. `lib/db/testDatabase.ts` opens a closable
connection rather than reusing `getDb()`, whose `globalThis` cache leaves Vitest
hanging on an open pool. The assertions read `constraint_name` off the driver
error's `cause`: Drizzle's own message is the failed SQL, so matching on it would
assert the query rather than the constraint.

**One value in the seed is not in the fixture.** `schedule_template.boundary_kind`
for OWN-V1 is `DATE`. Fixtures §3.8 shows that version entered with
`END_OF_SEMESTER` and then cut to 2026-10-21 by copy-on-write, and a cut date was
not entered by the teacher at all; `DATE` is the neutral value. The column is
display-only and `expand()` never reads it (schema §6), so nothing in T-005
depends on the choice. The other three versions carry the kinds §3.8 states.

**Findings F-3 and F-4** of `docs/architecture/design/schema.md` §12 are
unchanged by the implementation: neither `template_slot.lesson_number` nor
`day_override.lesson_number` is constrained to a number that has a
`bell_schedule` row (F-3, for T-005/T-010), and `day_override` still has no
per-day time columns (F-4).
